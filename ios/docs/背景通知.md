# iOS 上「手机主动响」到底能不能做

> 日期：2026-08-23 · 作者：ios-push
> 一句话结论：**能。而且比安卓版更省电、更可靠 —— 但那一声响必须经过 Apple 的 APNs，绕不过去。**
>
> ⚠️ **本文作者没有 Mac、没有 iPhone、没有开发者账号，一个字都没有实机验证过。**
> 凡是没有出处链接的地方，都显式标了「（未验证，推断）」。带链接的是查到的公开资料。

---

## 0. 先把问题问对

安卓版的做法（`android/.../watch/EventService.kt`）是：

```
前台服务 → 常驻一条 SSH 连接 → tail -f ~/.yxi/events.jsonl → 来事件就发本地通知
```

**手机自己持着那条连接。** 这在 iOS 上**做不到**，而且不是"难做"，是"系统不给"。

但 —— 换个角度，这件事在 iOS 上**根本不需要手机持连接**：

> **一条普通的 alert push，是操作系统投递的，不需要你的 App 活着，
> 甚至不需要你的 App 曾经在后台跑过，用户上滑杀掉它也照样响。**

所以真正的问题不是「iOS 上怎么常驻连接」，而是：

**「怎么让一条 push 进到 APNs、地址写着我这台 iPhone」。**

下面六条路，只有能回答这一句的才算数。

### 1.A 自建 Bark 服务器 —— **零成本、今天就能用、不经过任何第三方** ⭐

这是本文最重要的发现，值得单独说清楚。

[Bark](https://github.com/Finb/bark-server) 是一个开源的 iOS 推送工具，App Store 上有（[中国区可下](https://apps.apple.com/cn/app/bark-%E7%BB%99%E4%BD%A0%E7%9A%84%E6%89%8B%E6%9C%BA%E5%8F%91%E6%8E%A8%E9%80%81/id1403753865)，id `1403753865`），服务端可以自己部署。

**关键点：`bark-server` 的源码里内嵌了 Bark 自己的 APNs 私钥。**

已核实 —— [`apns/apns.go`](https://raw.githubusercontent.com/Finb/bark-server/master/apns/apns.go) 里是明文常量：

```go
const (
    topic  = "me.fin.bark"
    keyID  = "LH4T9V5U4R"
    teamID = "5U8LBRXG3A"
)
```

而 [`apns/apns_certs.go`](https://raw.githubusercontent.com/Finb/bark-server/master/apns/apns_certs.go) 里是一段明文的 `-----BEGIN PRIVATE KEY-----`（P-256 私钥，token-based auth 用的 .p8）。

**这意味着什么：**

```
你自己的服务器  ──HTTPS/JWT──▶  api.push.apple.com  ──▶  你的 iPhone
（跑 bark-server）                （Apple 的 APNs）        （App Store 的 Bark）
```

- **不经过 Bark 官方服务器**（`api.day.app` 完全不参与）
- **不经过我们**（本项目不需要跑任何服务器 —— PRD §2.6 的主张完整保住）
- **不需要 Apple 开发者账号、不需要 $99、不需要 Mac、不需要签名**

链路上只剩「用户自己的服务器」+「Apple 的 APNs」。这跟 PRD §2.7 拒绝 FCM 的理由**不冲突** ——
FCM 之所以被否，是因为它**强制我们长期跑一台中转服务器**；Bark 自建**没有那一环**。

**能力清单**（[官方文档](https://day.app/2018/06/bark-server-document/) / [FAQ](https://day.app/2021/06/barkfaq/)）：

| 参数 | 效果 | 对我们的用处 |
|---|---|---|
| `level=timeSensitive` | **穿透专注模式** | 「需要你」用这个 |
| `level=critical` | **穿透静音开关**（Bark 自己拿到了 Apple 的 critical alerts entitlement） | 睡觉时的紧急审批 |
| `call=1` | **连响 30 秒**，像来电 | 570 秒倒计时快到期时用 |
| `url=…` | 点通知跳链接 | **点一下直达 Yxi 的那一屏**（见下） |
| `group=` | 通知分组 | 按会话分组 |
| 端到端加密 | AES 自定义密钥，**服务器和 Apple 都看不到正文** | 消掉「摘要过 Apple」这个顾虑 |

**代价（不粉饰）：**

1. **通知上没有「批准 / 拒绝」按钮。** Bark 是通用推送 App，只能点击跳 URL，
   没有 `UNNotificationAction` 那样的自定义按钮。
   → 审批必须**点开 Yxi App** 才能做，比安卓版多一步。
   → 缓解：`url=yxi://approve?host=…&session=…` 深链直达那一屏。
   ⚠️ **未实测**：文档原话是「Click on the push notification to jump to the specified URL」，
   例子都是 `https://`。ios-push 和 team-lead 都读成「自定义 scheme 应该也吃」，但这是**同一句话的两次推断，不是两个证据**。
   万一不行：退回 `url=https://…`（要一台 HTTPS 服务器）或干脆不带 url，手动点开 App。
2. **弹通知的是 Bark，不是 Yxi。** ⚠️ **这是和安卓版最明显的体感差异。**
   锁屏上你看到的是 **Bark 的图标和名字**，通知的分组、声音、免打扰设置全都归 Bark 管
   （所有走 Bark 的推送混在一起，Yxi 的事件和你别的监控告警会同栏）。
   点进去能跳回 Yxi，但「谁在响」这件事跟安卓版不一样 —— 安卓那边是 Yxi 自己的图标、自己的通知渠道
   （`yxi.events` / `yxi.ongoing`，可以分别调优先级）。
   → 想要「Yxi 自己的图标 + 自己的渠道」就得走 §1.B。
3. **多装一个 App。** 用户手机上要有 Bark 才收得到。
4. **⚠️ 那把 APNs 私钥是全体自建用户共用的一把。** 它明文躺在开源仓库里
   （[`apns_certs.go`](https://raw.githubusercontent.com/Finb/bark-server/master/apns/apns_certs.go)，
   注释就写着 `// Bark push private key`）。也就是说：
   **Apple 一旦吊销或 Bark 主动轮换这把 key，全世界所有自建的 bark-server 同时哑掉**，
   要等上游发新版、你再重新部署一次。
   这是个真实的单点，虽然目前看它活得很好（仓库 MIT、3.6k star、2026-07 还在更新），
   但**选它就是接受这个风险**。
   → 兜底：§1.B 那条路（自己的 `.p8`）**不受任何影响** —— 掏了 $99 之后这个单点就消失了。
5. **通知内容过 Apple。** 用端到端加密可以让 Apple 只看到密文 —— 但「有一条通知」这个事实本身瞒不住。

**服务器侧要加什么**（⚠️ 本文作者未改任何 `server/` 下的文件，这是提案，等 team-lead 拍板）：

**不需要动 `yxi-hook`。** 最省的做法是一行 shell，跟着 `~/.yxi/events.jsonl` 走：

```sh
# ios 用户在自己服务器上跑一次（tmux / systemd / nohup 都行）
tail -Fn0 ~/.yxi/events.jsonl | while read -r line; do
  kind=$(printf '%s' "$line" | sed -n 's/.*"kind": *"\([^"]*\)".*/\1/p')
  [ "$kind" = "needs" ] || [ "$kind" = "done" ] || continue
  curl -sm5 -X POST "$BARK_URL" -H 'Content-Type: application/json' -d "$line" >/dev/null
done
```

**这条路完全是叠加的**：不碰 `yxi-hook`、不碰 `install.sh`、
安卓版一行都不受影响、不装也不影响 iOS 版的其它功能（看板/对话/终端/文件照常）。
——跟 PRD 附录 H「唯一必须装的是 yxi-hook」的纪律一致。

### 1.B 自己的 APNs key —— **掏了 $99 之后白捡的** ⭐

**这条不是「为了推送多花 $99」。** $99 是为了「App 装得上、别 7 天过期」掏的（见 `分发.md`）。
一旦掏了，推送是顺带的。

做法（[APNs token-based auth](https://www.w3tutorials.net/blog/how-to-send-apns-push-messages-using-apns-auth-key-and-standard-cli-tools/)）：

1. App Store Connect → Users and Access → Keys → APNs → 生成一个 `.p8`（**你自己的**）
2. `.p8` + Key ID + Team ID + Bundle ID 放到**你自己的服务器**上
3. 服务器用 ES256 签一个 JWT（有效期 ≤1 小时），
   `POST https://api.push.apple.com/3/device/<token>`，带 `authorization: bearer <jwt>`

链路跟 Bark 方案**一模一样**（你的服务器 → APNs → 你的手机），
区别只是那个 .p8 是你自己的，通知是 **Yxi 自己的**。于是解锁两样东西：

| 解锁 | 说明 |
|---|---|
| **通知上的按钮** | `UNNotificationAction` → 通知上直接「1. Yes / 3. No」，对齐安卓版体验 |
| **Live Activity** | 灵动岛/锁屏的审批倒计时（§1.F） |

⚠️ **通知按钮的后台窗口有多长 —— 这是本方案最大的未知数。**
点了非 `.foreground` 的通知按钮，App 被在后台唤起执行 `didReceive response:`，
查到的说法是**约 10 秒**（[Apple 开发者论坛](https://developer.apple.com/forums/thread/764912)，
且 Apple 明说这个值不保证、不该写进业务逻辑）。

我们要在这个窗口里干的事是：**SSH 握手 → `capture-pane` 重新确认提示没变 → `send-keys`。**
安卓版 `EventService.answer()` 那套「送键前必须重新抓屏确认指纹」的纪律**一条都不能省**
（理由见那段注释：提示可能已经被别处答掉了，换成了另一个问题）。

蜂窝网络下 SSH 握手大概 1~3 秒，两次往返，**理论上塞得进 10 秒**（未验证，推断）。
但这是在赌网络。**建议的降级设计：**

- 按钮默认设成 `.foreground`（点了就开 App 到那一屏，用户看着按）—— 慢一步，但绝不会「批错」
- 后台直批当作**可选开关**，且失败时必须发一条「没替你按，点开看看」的通知
  （安卓版 `note()` 已经是这个模式，照搬）

### 1.C Background App Refresh / BGTaskScheduler —— ❌ **达不到「几秒内」**

`BGAppRefreshTaskRequest.earliestBeginDate` 的语义是「**不早于**这个时间」，
**不是**「到点就跑」。系统按电量、温度、网络、你开这个 App 的频率自己决定跑不跑、什么时候跑
（[参考](https://mertbulan.com/programming/dont-rely-on-bgapprefreshtask-for-your-apps-business-logic)）：

> Background execution is a contract, not a guarantee. The system decides: when · if · how long · with what priority.

**用它来实现「Claude 等你决定时立刻响」是不成立的** —— 它可能几小时才跑一次，
也可能因为你今天没打开过这个 App 就干脆不跑。

**iOS 26 的新 API 也救不了。** `BGContinuedProcessingTask`（WWDC25 引入）
要求**必须由用户在前台的一次点击直接发起**，用来把一个已经开始的任务（导出/上传/压缩）跑完，
系统给它一个 Live Activity 显示进度（[WWDC25 227](https://developer.apple.com/videos/play/wwdc2025/227/)）。
——它解决的是「让用户发起的活干完」，不是「等服务器来事」。**用不上。**

### 1.D Silent push（`content-available: 1`）—— ❌ **不可靠，而且没必要**

- 必须用 `apns-push-type: background` + `apns-priority: 5`；
  优先级 5 的通知**会被合并成批投递、会被限流、某些情况下直接不投**
  （[Apple 文档口径](https://help.sap.com/doc/f53c64b93e5140918d676b927a3cd65b/Cloud/en-US/docs-en/guides/features/push/api/provider/apns.html)）
- 业界普遍口径：**每台设备每小时超过 2~3 条就开始丢**
  （[Pushy](https://support.pushy.me/hc/en-us/articles/360043925371-How-can-I-send-silent-background-notifications-on-iOS)）
- 用户上滑杀掉 App 后不投递

**但更重要的是：我们不需要它。** silent push 的用途是「悄悄把数据更新一下」，
而我们要的是「把用户叫醒」—— 那是 alert push 的活，**alert push 不需要 App 活着**。
把 silent push 塞进来只会多一条不可靠的路径。

### 1.E VoIP push（PushKit）—— ❌ **这条要更正任务书里的说法**

> 任务书写的是「VoIP push 会被审核拒，但侧载不过审 —— 这个区别要说」。
> **这个区别在这里不成立：侧载救不了 VoIP push。**

iOS 13 起，收到 VoIP push 后**必须**在 `didReceiveIncomingPush` 里向 CallKit 报告一通来电，
否则 **操作系统直接把 App 干掉**，崩溃信息是：

```
Terminating app due to uncaught exception 'NSInternalInconsistencyException',
reason: 'PushKit apps that use VoIP push must link either CallKit or
         IncomingCallNotifications frameworks.'
```

反复不报告，系统会**彻底不再为 VoIP push 拉起你的 App**
（[Apple 文档](https://developer.apple.com/documentation/PushKit/responding-to-voip-notifications-from-pushkit)、
[Twilio #251](https://github.com/twilio/voice-quickstart-ios/issues/251)）。

**这是 OS 强制的，跟上不上架、过不过审毫无关系。**

**而且用户在中国 —— 这里还有第二重死路。**
CallKit 在中国大陆被停用（2018 年起，工信部要求），
Apple 会拒绝中国区使用 CallKit 的 App，设备上 `CXProvider.isSupported` 为假
（[Apple 论坛 121088](https://developer.apple.com/forums/thread/121088)、
[121890](https://developer.apple.com/forums/thread/121890)）。
**没有 CallKit → 不能用 PushKit。**

→ **这条路彻底封死，别再考虑。**

### 1.F Live Activities / 灵动岛 —— ✅ 做，但它是「响完之后的展示」

**先说清楚定位**：Live Activity **不是唤醒手段**，它是「已经有一条 push 进来之后，
把状态挂在锁屏和灵动岛上」。所以它依赖 §1.B（自己的 APNs），不能单独成立。

- 需要在 Xcode 里给 App 加 **Push Notifications capability** → **要 $99 账号**
  （[Apple 文档](https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications)）
- **iOS 17.2 起支持 push-to-start**：服务器拿 `pushToStartToken` 就能**远程开启**一个 Live Activity，
  App 不必在前台（[参考](https://www.braze.com/resources/articles/launch-an-ios-live-activity-with-new-push-to-start-tokens)）。
  17.2 之前只能 App 自己在前台 `request(attributes:…)` 起。
- payload 里带 `alert` 字段可以**点亮屏幕 + 灵动岛展开**。

**最佳用法跟安卓版 PRD §2.7 定的一模一样：审批倒计时。**
hook 阻塞有个真实的 570 秒截止时间，天然是进度条素材：

```
🔴 cc-mail 等待授权 · 还剩 8:32
   [批准]  [拒绝]
```

**iOS 这里反而比 Android 好做**：灵动岛是 iPhone 的原生系统能力，
不像安卓那边要么等 Android 16 Live Updates（API 36，且完整体验先在 Pixel 上放）、
要么去求厂商开放私有的「灵动胶囊」（决策 D9 已判定走不通）。

### 1.G Local Push Connectivity（`NEAppPushProvider`）—— ❌ 拿不到，且蜂窝无效

**这是 iOS 上唯一一个真正对应「安卓前台服务常驻长连接」的东西**，值得写清楚为什么用不了。

它是 iOS 14 引入的 NetworkExtension：系统在**匹配到指定 Wi-Fi SSID / 私有 LTE** 时
拉起一个扩展进程，这个进程**独立于 App 生命周期**维持自己的长连接、自己发通知
（[Apple 文档](https://developer.apple.com/documentation/networkextension/neapppushprovider)、
[WWDC20 10113](https://developer.apple.com/videos/play/wwdc2020/10113/)）。

两条硬拦路：

1. **entitlement 受限。** `com.apple.developer.networking.networkextension` = `app-push-provider`
   **必须向 Apple 单独申请**，而且要给出一个「我的部署环境连不上 APNs」的具体理由。
   它的设计场景是邮轮、飞机、医院、园区 —— **不是「我不想过 APNs」**。
   我们的场景（用户在外面用 4G）恰恰是 APNs 完全可用的场景 → **申请理由不成立**。
2. **只在声明的 Wi-Fi / 私有 LTE 上生效，蜂窝网络无效。**
   而本项目的核心场景就是 PRD §4 的「地铁上」「等电梯」——**全是蜂窝**。
   就算拿到 entitlement，出门就失效。

### 1.H 保活歪招 —— ❌ 明确不做（写在这里是为了把这条路封死）

侧载确实不过审，所以「App Store 会拒」对我们不构成约束。但这三条仍然不该走：

| 招 | 能不能跑 | 为什么还是不做 |
|---|---|---|
| **播放静音音频** | 大概还能（未验证） | 显著耗电；**抢占音频会话**（你放歌它就打架）；Apple 明确说这是滥用 background audio 模式（[论坛](https://developer.apple.com/forums/thread/105443)） |
| **significant location change** | 能，但只在**位置变化**时把 App 拉起 | 你坐家里不动 → 它就不响。而且要常开定位权限，耗电 + 隐私。**功能上根本不满足需求** |
| **VPN 扩展 `NEPacketTunnelProvider`** | ✅ 技术上真能常驻（系统级进程，独立于 App，蜂窝也有效） | 要把整机流量接管进你的"VPN"。**为收个通知付这个代价是荒唐的**；且 NetworkExtension 也要账号。<br>// ⚠️ 未验证：packet-tunnel-provider 对普通付费账号是否自助可用 |

**共同的问题：它们都在跟操作系统对着干。** 而 §1.A 已经给了一条**顺着系统走、零成本、秒级**的路 —— 没有理由走歪招。

### 1.I 什么都不做，只在 App 打开时轮询 —— 兜底，但等于砍掉「主动」

- App 在**前台**时：跟安卓版一样开一条 SSH `tail -f`，收到事件发**本地通知**
  （本地通知不需要任何 entitlement，**免费账号也能用**）
- App 一切后台：`beginBackgroundTask` 给的窗口 iOS 13 起从 3 分钟砍到 **约 30 秒**
  （[参考](https://dev.to/tejeshwargill/all-about-handling-background-tasks-in-ios-13-4gc0)），
  30 秒后进程挂起，SSH 连接断

→ **只要你没盯着手机，它就不会响。** PRD §3 目标 5「Claude 干完活 / 要授权 → 手机主动响」直接落空。

**这条只能当「A 和 B 都没配」时的降级说明文案**，不能当方案。

---

## 2. 明确推荐

**分两层，可以同时上，互不冲突，先后独立。**

### 第 0 层 —— Bark 负责「响」（今天就能有，零成本）

```
Claude Code hook → ~/.yxi/events.jsonl → 5 行 tail 脚本 → 自建 bark-server
                                                           → Apple APNs → iPhone 响
```

- **成本：0 元。** 不要开发者账号、不要 Mac、不要签名
- **Yxi iOS App 完全不参与这一层** → 即使 App 还没写完、或者签名过期打不开了，
  「Claude 找你」这件事**照样不丢**
- 审批要点开 App（多一步），或者点开 Bark 通知里的深链
- ⚠️ 两条要认下来的：**弹通知的是 Bark 不是 Yxi**（图标/名字/通知设置都是 Bark 的）；
  **那把 APNs 私钥全世界共用一把**，被轮换时所有自建 server 一起哑（§1.A 代价 2 和 4）
- 服务器侧改动 = **一个可选的独立脚本**，不碰 `yxi-hook` / `install.sh`，安卓版零影响

### 第 1 层 —— 掏了 $99 之后，Yxi 自己的 APNs

- 自己的 `.p8` 放自己服务器，直连 `api.push.apple.com`
- 解锁：**通知上直接批准**（对齐安卓版）+ **灵动岛审批倒计时**
- 通知按钮的后台窗口只有约 10 秒 → **默认走 `.foreground`（点了开 App），后台直批做成可选开关**
- **$99 本来就得掏**（否则 App 7 天就打不开，见 `分发.md`），所以这一层的边际成本是 0

## 3. 那句「不经过任何第三方服务器」要精确化

这是本文唯一需要用户重新拍板的地方。

PRD §2.6 / §2.7 的主张是「**我们不跑任何服务器**」，
拒绝 FCM 的理由是它**强制我们长期跑一台中转机**，且**用户的通知内容全部经过我们**。

**iOS 上这条主张仍然成立，一个字都不用改**，因为：

| | FCM（被否） | iOS 走 APNs（推荐） |
|---|---|---|
| 要**我们**跑服务器吗 | ✅ 要（致命） | ❌ **不要** |
| 通知经过**我们**吗 | ✅ 经过（致命） | ❌ **不经过** |
| 经过平台方吗 | 谷歌 | Apple |
| 平台方看得到内容吗 | 看得到 | Bark 端到端加密后**只看得到密文** |
| 用户手机上默认可用吗 | ❌ 荣耀 Magic7 默认关 GMS（D8 的直接依据） | ✅ **APNs 是 iOS 的一部分，人人都在用，中国可用** |

**FCM 被否的两条理由，在 APNs 这里一条都不成立。**
`FCM ≠ APNs`：FCM 是「谷歌的一个云服务，我们得去接」，
APNs 是「iPhone 收通知的唯一系统通道，你已经在用了」。

一句话：**「不经过任何第三方服务器」的准确表述是「不经过我们的服务器」。**
Apple 的 APNs 是操作系统的一部分，不是我们引入的中间商 —— 在 iOS 上它没有替代品（§1.G 已证）。

---

## 4. 最终答案

> **「iOS 版能不能做到 Claude 需要你时手机会响？」**
>
> **能，秒级，而且比安卓版更省电、更可靠。**
>
> - 不需要常驻 SSH 连接 → **不耗电**（安卓版日常掉几个百分点，iOS 这里接近 0）
> - 不需要跟国产 ROM 的后台管控搏斗 → **不会被杀**（PRD §2.7 那三条「真实代价」在 iOS 上全部消失）
> - 手机重启、App 被上滑杀掉、几天没打开 —— **照响**
>
> **代价三条：**
> 1. 那一声响必须经过 Apple 的 APNs（iOS 上唯一的合法唤醒通道，§1.G 已证无替代）
> 2. 零成本方案（Bark）下有三样东西要认：**通知上没有批准按钮**（审批要点开 App）、
>    **弹通知的是 Bark 不是 Yxi**（图标和通知设置都是 Bark 的）、
>    **那把 APNs 私钥全世界共用一把**（被轮换时所有自建 server 一起哑）
> 3. 想要通知上直接批 + 灵动岛倒计时 + 消掉上面那三条 → 掏 $99（但那笔钱本来就得掏，见 `分发.md`）
